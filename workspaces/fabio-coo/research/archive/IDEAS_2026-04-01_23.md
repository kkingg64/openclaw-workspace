## 🔍 Top 3 Discoveries

### 1. 🏗️ "Skills as Architecture" — 點解 90%嘅 AI Agent Skills都係垃圾

**Insight:** 大多數 AI agent skills 失敗唔係因為「AI 唔夠好」，而係因為 **skill 架構設計從一開始就錯咗**。真正好嘅 skill 係「Composable, Reusable, Testable」，而唔係一堆包在一起嘅 prompt。

**壞嘅 Skill 架構常見問題：**
```
❌ "God Prompt" 架構：
▸ 一個 skill 做晒所有嘢（3000 tokens 單一 prompt）
▸ 問題：難以測試、難以 debug、難以迭代
▸ AI 無法選擇性使用當中某部分

❌ "Hardcoded Workflow" 架構：
▸ 步驟寫死，唔准許 AI 靈活調整
▸ 問題：遇到邊界情況就fail，無法適應新情況
▸ 把 AI 變成 automation script，唔係 intelligent agent

❌ "Prompt + Code 分離" 架構：
▸ Prompt 响呢度，code 响另外地方
▸ 問題：無法和 AI context 完全整合，輸出唔穩定

❌ "一次性使用" 架構：
▸ Skill 每次使用都重新嚟，冇狀態
▸ 問題：唔記得之前做咗乜，無法建立複雜工作流程
```

**好嘅 Skill 架構 — "Three-Layer Model"：**

```
Layer 1: Intent Classifier（意圖分類）
▸ 快速識別用家想要乜
▸ 輸出：精確分類（例如："database_migration" vs "new_feature"）
▸ 特性： lightweight, deterministic, 可快速路由

Layer 2: Skill Selector（技能選擇）
▸ 根據 Intent 選擇用邊個 skill / skill 組合
▸ 特性：可配置， skill 之間可以dependencies

Layer 3: Execution Engine（執行引擎）
▸ 真正做嘢嘅 layer
▸ 包含：prompt templates + code snippets + validation
▸ 特性：idempotent（可以安全地跑多次）、testable
```

**"Goldilocks Scope" 原則 — Skill 大小幾啱？**

```
太多 → Skill 太闊（"幫我做個SaaS"）
▸ 問題：冇人知幾時用、幾時唔用
▸ 結果：變成另一個 "god prompt"

太少 → Skill 太窄（"幫我寫呢個函數"）
▸ 問題：無法建立有意義嘅工作流程
▸ 結果：變成一支超級強嘅 toothpick

✅ 啱啱好 → "End-to-End Task Unit"（"幫我設置 Stripe Billing"）
▸ 一個 skill 完成一個有意義嘅完整任務
▸ 可獨立運作，可組合使用
▸ 例如："Setup Stripe Billing" = 頁面 + webhook + 錯誤處理 + 測試
```

**Skills Composition Patterns（2026 最新）：**

| Pattern | 點解有用 | 適合場景 |
|---------|----------|----------|
| **Sequential** (A→B→C) | 簡單直接 | 標準 workflow（auth→db→api） |
| **Parallel** (A‖B‖C) | 節省時間 | 獨立任务（test + lint + format） |
| **Conditional** (if X→A else→B) | 智能分流 | decision-making tasks |
| **Fallback** (try A, fail→B) | 穩定性 | mission-critical operations |
| **Loop** (repeat until X) | 迭代優化 | testing, refactoring, data processing |
| **Meta-skill** (skill about skills) | 自我改進 | 幫 AI 選擇用邊個 skill |

**Skills 依賴管理 — 最重要但最容易被忽視：**

```
好嘅 Dependencies 聲明：
┌─────────────────────────────────────┐
│ skill: stripe_billing              │
│ depends_on:                        │
│   - filesystem (write files)      │
│   - http (api calls)               │
│   - test_runner (validation)       │
│ provides:                          │
│   - stripe_webhook_endpoint        │
│   - subscription_management        │
│   - usage_tracking                 │
└─────────────────────────────────────┘

好處：
▸ AI 可以自動檢查 dependencies 是否滿足
▸ 可以自動安裝缺失的 dependencies
▸ 避免 "某個 skill 用到但冇 declare" 的隱形依賴
```

**Commercial Value:**
- **Skills architecture consultant:** 幫 teams 設計公司內部 skills 架構 → $3K-10K
- **Skills testing framework:** 自動化測試 skills 可靠性 → SaaS subscription
- **Skills composition engine:** 幫 builder 組裝 skills workflow → tooling license
- **Skills quality audit service:** 審計現有 skills → 指出架構問題 + 改進建議 → $500-2K/skill

**建議行動：** 唔好立即寫 skill。先問：「呢個 skill 係為邊個 scenario？幾時用？幾時唔用？」如果答案模糊，skill 太大。如果需要15個前置步驟，skill 太窄。

### 2. 🎯 OpenClaw Skills vs Claude Code vs Cursor — 三強生態點評

**Insight:** 2026 年嘅 AI coding agent skills 生態已經形成三個明顯流派——**OpenClaw（灵活多用途）、Claude Code（quality-first）、Cursor（IDE整合）**。明白佢哋嘅設計哲學，先可以揀啱工具。

**三平台Skills系統深度比較：**

| 維度 | OpenClaw | Claude Code | Cursor |
|------|----------|-------------|--------|
| **Skills 定位** | 第一 class citizen，核心架構 | 起步階段，官方 marketplace 籌備中 | IDE extension，rules-based |
| **使用方式** | 透過 tool calls 主動觸發 | 透過 prompt 指示 | 透過 .cursorrules 文件 |
| **可組合性** | ⭐⭐⭐⭐⭐ 高度可組合 | ⭐⭐⭐⭐ 依賴 prompt engineering | ⭐⭐⭐ 有限（file-based） |
| **靈活性** | ⭐⭐⭐⭐⭐ 可以runtime調整 | ⭐⭐⭐⭐ 取決於 prompt | ⭐⭐⭐ 受限於 IDE |
| **生态成熟度** | ⭐⭐⭐ 新但快速發展 | ⭐⭐⭐⭐ 快速追趕 | ⭐⭐⭐⭐ 有社區 |
| **企業適用性** | ⭐⭐⭐⭐⭐ 灵活+安全 | ⭐⭐⭐⭐ 品質導向 | ⭐⭐⭐ 中（VSCode限定） |
| **跨平台能力** | ⭐⭐⭐⭐⭐ 天然跨平台 | ⭐⭐⭐⭐ 通過 API | ⭐⭐⭐ 限 Cursor IDE |

**OpenClaw Skills 架構哲學：**
```
核心思想：Skills are first-class agents, not prompts

┌─────────────────────────────────────────────┐
│ OpenClaw Skill =                           │
│   - Intent patterns (何時觸發)             │
│   - Action sequences (做乜)                 │
│   - Validation logic (點樣驗證結果)         │
│   - Error recovery (fail咗點算)             │
│   - Metadata (描述、作者、版本)             │
└─────────────────────────────────────────────┘

優勢：
▸ Skills 可以互相調用（composition）
▸ Skills 可以有狀態（stateful execution）
▸ Skills 可以聲明 dependencies（自動安裝）
▸ Skills 可以被 versioned（版本控制）

特别適合：
✅ 需要组合多個工具的複雜任務
✅ 需要安全審計的企業環境
✅ 需要高度定制的個人 workflow
```

**Claude Code Skills 架構哲學：**
```
核心思想：Quality through constraints

┌─────────────────────────────────────────────┐
│ Claude Code 理想 workflow：                  │
│   - Human 描述目標（高層次意圖）             │
│   - Claude 理解 + 規劃                      │
│   - Claude 執行 + 解釋決策                  │
│   - Human 審批 / 調整                       │
└─────────────────────────────────────────────┘

Skills 實現方式：
▸ Project-specific instructions（per-project config）
▸ Tool use patterns（定義點樣用 tools）
▸ Output format standards（標準化輸出格式）

特别適合：
✅ 需要深度 reasoning 的任務
✅ 複雜架構決策（system design）
✅ 需要 human-in-the-loop 的場景
```

**Cursor Rules 架構哲學：**
```
核心思想：IDE-level behavioral rules

┌─────────────────────────────────────────────┐
│ .cursorrules 文件包含：                     │
│   - 項目特定 coding style                   │
│   - 技術棧偏好                             │
│   - 檔案組織規則                            │
│   - 工作流程期望                           │
└─────────────────────────────────────────────┘

限制：
▸ 綁定特定 project（唔容易 transfer）
▸ 主要是coding style，唔涉及高層次 task
▸ 依賴 IDE（離開 Cursor 就冇用）

特别適合：
✅ 單一 project 內的團隊 coding standards
✅ 小團隊快速建立共識
✅ 已經用開 Cursor 的個人 makers
```

- **OpenClaw skills training:** 企業內部培訓 → $1K-3K per session

### 3. 🔬 "Testing Skills" —點樣確保你嘅 Skill 靠譜？

**Insight:** Skills 嘅 quality problem 係成個生態最大嘅 blocker——**冇人知點樣測試一個 skill**。呢個係可以建立巨大競爭優勢嘅地方。

**為何 Skills Testing 特別難：**
```
傳統 software testing：
▸ 輸入 → 確定輸出
▸ 可以assert結果
▸ 可以automate

Skills testing：
▸ 輸入 → AI interpretation → 不確定輸出
▸ 同一輸入可能有多個「啱」輸出
▸ 難以判斷「quality」——主觀因素多
▸ AI model 版本更新可能破壞現有 behavior
```

**Skills Testing Framework（2026 Best Practices）：**

**Test Category 1: Functional Tests（功能測試）**

```
定義：Skill 能否完成佢聲稱可以做的任務

測試方法：
┌────────────────────────────────────────────┐
│ Test Case: "stripe_billing skill"          │
│                                            │
│ Input: "Add monthly subscription to $29"   │
│ Expected:                                  │
│   - Stripe subscription created            │
│   - Webhook endpoint configured            │
│   - Customer portal updated                │
│   - Test coverage included                 │
│                                            │
│ Pass criteria:                             │
│   ✅ All 4 components present               │
│   ✅ Code is idiomatic (no syntax errors)  │
│   ✅ Follows project conventions           │
└────────────────────────────────────────────┘

自動化方式：
▸ Output parsing（檢查結構是否完整）
▸ Code quality checks（lint + type check）
▸ Dry run（有 mock mode 可以試）
```

**Test Category 2: Reliability Tests（穩定性測試）**

```
定義：Skill 每次運作結果係咪一致

測試方法：
▸ 同一 input 跑 5 次
▸ 結果應該大致相同（允許非關鍵性差異）
▸ 關鍵組件必須 100% 一致

Pass criteria：
▸ 核心邏輯 100% 一致
▸ 輸出格式 100% 一致
▸ 非關鍵部分（variable names, comments）可以略有不同
```

**Test Category 3: Edge Case Tests（邊界情況測試）**

```
定義：Skill 遇到非標準情況時點樣 handle

測試 cases：
▸ "What if Stripe API is down?"
▸ "What if user has no Stripe account?"
▸ "What if the price is $0?"
▸ "What if the product name has special characters?"

Pass criteria：
▸ Skill唔會crash
▸ 提供有意義的 error message
▸ 可以從 error 中恢復
```

**Test Category 4: Regression Tests（回歸測試）**

```
定義：當 AI model 或環境更新，舊有 skills 仍然正常運作

測試方法：
▸ 建立 golden test cases（已知的 good outputs）
▸ 每當有 model update，重新跑一次
▸ 比較結果是否顯著偏離

Pass criteria：
▸ Core functionality score > 90% match
▸ 沒有 regression in critical paths

⚠️ 呢個係最多人忽略的測試
▸ 今日 work唔代表明日 work
▸ AI model 更新可能破壞 subtle behaviors
```

**Skills Testing 自動化工具（2026 Landscape）：**

| 工具 | 用途 | 限制 |
|------|------|------|
| **Manual testing** | 簡單 skills | 不可擴展 |
| **Output diffing** | 結構化 outputs | 無法評估質量 |
| **LLM-as-judge** | 主觀 quality 評估 | 昂貴，主觀 |
| **Formal verification** | 數學證明正確性 | 複雜，只適合特定類型 |
| **Property-based testing** | 測試 invariants | 適用於有數學性質的 skills |

**"Skills Test-Driven Development" 流程（推薦）：**

```
1. 先寫 Test Cases（未寫 skill 前）
   ↓
2. 定義 "done" 的標準
   ↓
3. 寫最簡單的 skill 版本
   ↓
4. 跑測試，睇邊個 fail
   ↓
5. 迭代 skill 直到全部 pass
   ↓
6. 加入 edge case tests
   ↓
7. 重複 3-7 直到穩定
   ↓
8. 加入 regression test suite
```

**Commercial Value:**
- **Skills testing SaaS platform:** 自動化 skills testing + regression detection → $99-499/month
- **Skills test engineer:** 幫公司建立 skills testing pipeline → $150-300/hour
- **Skills quality certification:** 認證某個 skill 通過某級別測試 → certification fee
- **Skills insurance:** 如果 skill fail 導致損失可以 claim → 新型保險產品

**建議行動：** 即使你係個人 maker，都應該建立起碼 3 個 test cases 來 test 每個 skill。用 「input → expected output」格式，保存喺 `skills/[name]/tests/` folder。呢個investment 會喺 long run 為你省大量 debugging 時間。

## 📊 Skills Development Lifecycle（完整流程）

```
Phase 1: Discovery（發現階段）
▸ 識別反複出現的 workflow
▸ 量化時間價值：「呢個任務我每月做幾次？每次幾耐？」
▸ 評估是否可以 skill 化

Phase 2: Design（設計階段）
▸ 定義 scope（Goldilocks scope）
▸ 設計 interface（inputs → outputs）
▸ 規劃 composition（點樣同其他 skills 互動）
▸ 撰寫 test cases

Phase 3: Implementation（開發階段）
▸ 順序：Test → Code → Test → Refine
▸ 每個 component 完成後立即測試
▸ 保持 skill 簡單——複雜功能拆分成多個 skills

Phase 4: Testing（測試階段）
▸ Functional tests（全部通過）
▸ Reliability tests（5x 一致性）
▸ Edge case tests（防禦性編碼）
▸ Regression tests（model update 兼容性）

Phase 5: Documentation（文檔階段）
▸ README.md（係乜、點用、何時用）
▸ Examples（常見 use cases）
▸ Limitations（已知限制）
▸ Dependencies（需要乜嘢前置條件）

Phase 6: Distribution（分發階段）
▸ 選擇平台（Gumroad, Lemonsqueezy, 直銷）
▸ 設置 pricing
▸ 建立 landing page
▸ 收集首批用家 feedback

Phase 7: Maintenance（維護階段）
▸ 定期更新（每當底層工具改變）
▸ 根據用家 feedback 迭代
▸ 監控 production 使用情况
▸ 準備 deprecation plan（如果需要放棄）
```
